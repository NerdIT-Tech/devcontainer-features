# Contributing

Thank you for your interest in contributing to NerdIT-Tech Dev Container Features.

## Development setup

All tool versions are pinned via [mise](https://mise.jdx.dev/) so local runs match CI.

```sh
# Install mise (one-time)
curl https://mise.run | sh

# Install pinned tools (one-time, or when .mise.toml changes)
mise install
```

## Running checks locally

```sh
mise run validate          # JSON + bash -n syntax checks
mise run lint-yaml         # yamllint
mise run lint-actions      # actionlint
mise run test -- <feature> [baseImage]   # autogenerated test path
mise run test-scenarios -- <feature>     # scenario tests (volume/lifecycle)
```

The default base image is `mcr.microsoft.com/devcontainers/base:ubuntu`.

## Adding a new feature

1. Create `src/<feature>/` with:
   - `devcontainer-feature.json` — manifest (id, version, name, description, options, mounts, etc.)
   - `install.sh` — build-time install script (runs as root, places files only)
   - `onCreate.sh` — user-scoped setup (symlinks, XDG wiring) if needed
   - `version.txt` — initial version (e.g. `0.1.0`)
   - `CHANGELOG.md` — initial changelog

2. Create `test/<feature>/` with either:
   - `test.sh` — standalone test (for simple install features), or
   - `scenarios.json` + scenario scripts (for volume/lifecycle features)

3. Register the feature in `.release-please-config.json` (release-type `simple`).

4. Wire the feature into `.github/workflows/test-features.yml` matrix lists (`autogen_all` or `scenarios_all`).

5. Open a PR with a [Conventional Commits](#commit-conventions) message.

## Code style

### Shell scripts

- Start with `#!/usr/bin/env bash` and `set -euo pipefail`.
- Use `command -v` to check for dependencies before using them.
- Guard against re-running (idempotency): skip if already installed.
- Clean up temp files and apt lists (`rm -rf /var/lib/apt/lists/*`).

### install.sh vs onCreate.sh

- `install.sh` runs as **root** at image build. It may only place files (e.g. copy `onCreate.sh` to `/usr/local/share/<feature>/`). Never touch remote-user home or volumes.
- `onCreate.sh` runs as the **remote user** after volumes are mounted. This is where symlinks into volumes, XDG wiring, and `chown` of mount points happen.

### devcontainer-feature.json

- `id` matches the directory name.
- `version` is managed by release-please — never edit by hand.
- Use `options` for user-configurable values; they arrive as env vars (UPPERCASED option key).
- Use `mounts` for named volumes; use `onCreateCommand` to run user-scoped setup.
- Use `installsAfter` to declare dependencies on other features (e.g. `ghcr.io/devcontainers/features/common-utils`).

## Commit conventions

Conventional Commits are enforced in CI. Format: `<type>(<scope>): <subject>`

Types: `feat`, `fix`, `docs`, `refactor`, `perf`, `chore`, `test`, `ci`

Examples:
- `feat(opencode): add version option for pinning releases`
- `fix(claude-cache): handle pre-existing ~/.claude directory`
- `docs: update contributing guide`

## Release process

Releases are automated via [release-please](https://github.com/googleapis/release-please):

1. Merge a PR to `main` with a Conventional Commits message.
2. Release-please opens a release PR with version bumps and changelog updates.
3. Merge the release PR.
4. The `release.yml` workflow triggers on the version tag (`<id>/v*`), builds the feature, and publishes to `ghcr.io/nerdit-tech/devcontainer-features/<id>:<major>`.

You can also trigger a manual release via `workflow_dispatch` on the `Release dev container features` workflow.

## Architecture decisions

See `docs/adrs/` for binding rules (R-FEAT-*, R-TEST-*, R-SHELL-*). Read these before editing `src/` or `test/`.
